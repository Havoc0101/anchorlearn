## 2. 两个人分别负责什么

前端是用户看到和操作的页面；后端是处理录音、调用 AI、保存数据的程序。接口是双方约定的传递数据方式。

| 人员 | 主责 | 具体工作 | 交付物 |
| --- | --- | --- | --- |
| 你，简称 A | 前端、交互、组织整合 | 上传与播放录音、展示和核对任务、建议日程、提醒展示、进度反馈、错误提示；组织完整演示 | 能操作的页面、接口调用、用户操作验收记录 |
| 另一位技术同学，简称 B | 后端、转写、学习助手 Agent、数据保存 | 音频转文字、任务提取、原话位置、日程建议、任务匹配和变更、保存与查询、服务错误处理 | 可实际调用的接口、真实模型结果、任务与提醒记录、后端验证记录 |
| A＋B | 共同约定与联调 | 统一数据格式和启动方式、接通双方代码、检查完整流程 | 两人的环境都能运行的版本 |

整合由 A 组织，但 B 要一起排查后端和接口问题。这个分工不表示 A 承担全部测试，也不表示 B 的工作只需写一份提示词。

建议按上述边界划分页面模块、后端模块和公共接口文档。目录结构等选定技术栈后再确定，不为了分工额外拆成多个仓库或多个 Agent。

## 3. 最小 Demo 的终点

做到下面这条完整流程，即可停止扩展、准备演示：

```text
导入第一段真实音频
  → 实际转写
  → Agent 提取 3 项任务与原话依据
  → 用户集中核对并保存
  → 生成按天安排的建议日程和当前一步
  → 展示应用内提醒
导入第二段延期音频
  → Agent 识别已有任务与新期限
  → 展示原安排、新安排和原话
  → 用户确认
  → 原任务、建议日程和提醒记录同步更新
```

页面开发早期可以使用明确标注的示例数据；最终演示必须接上真实转写和模型处理。应用内提醒展示不等同于手机锁屏通知，也不承诺关闭网页后仍能提醒。

## 6. 必须共同约定的接口与数据

以下是需要提供的操作，不是已经实现的 API。B 起草具体路径和字段，A 按约定调用；建议把最终版本集中写入一份接口文档。

| 操作 | A 传给后端什么 | B 返回什么 |
| --- | --- | --- |
| 上传与处理录音 | 音频、录音日期、时区、课程或来源上下文 | 录音标识、处理状态、错误或完成结果 |
| 读取分析结果 | 录音标识 | 带时间位置的转写、任务草稿、待确认问题 |
| 保存核对结果 | 草稿标识、用户修改后的任务 | 正式任务标识、保存结果 |
| 生成／调整建议日程 | 已确认任务、明确的用户反馈 | 建议日程、当前一步、理由和相关估计 |
| 分析任务变更 | 新录音或其转写、相关现有任务 | 候选关联任务、原值、新值、原话、待确认原因 |
| 确认变更 | 变更标识、用户选择的关联任务 | 更新后的任务、日程和提醒记录 |
| 更新进度 | 任务标识、完成状态或已完成步骤 | 最新状态、需要用户接受的新日程建议 |
| 读取／调整提醒 | 任务或提醒标识、提醒偏好 | 今日提醒、截止前提醒、启用或关闭状态 |
| 删除演示记录 | 指定录音或任务标识 | 删除结果及仍保留哪些关联数据 |

需要统一的字段：

- **录音：**稳定标识、来源／课程、录音日期与时区、音频位置、处理状态。
- **转写片段：**文字、起止时间位置、所属录音。回听位置来自转写时间信息，不能由语言模型编造。
- **任务：**稳定标识、名称、要求、截止日期及是否有明确钟点、状态、原话片段、待确认项。
- **建议日程：**任务／步骤标识、建议日期、当前一步、简短理由、AI 估计标记。
- **变更：**目标任务或候选列表、原值、新值、证据、是否已确认；没有确认的变更不覆盖正式记录。
- **提醒：**对应任务、类型、提醒时间、启用／失效状态；任务变更后旧提醒可追踪。
- **错误：**用户能理解的说明、是否可重试；页面需要区分处理中、失败、成功但未找到任务。

尚未确定截止时间时使用明确的空值与待确认状态；仅知道日期时不把系统默认钟点伪装成老师给出的准确期限。“明天”“下周一”等相对日期应依据录音时间和时区解析，有歧义就提示确认。

依赖：P2、P3、P6、P8。这一阶段先使用真实录音对应的文字，便于定位问题；它只是中间检查点，不能代替最终音频 Demo。

- [ ] **T1｜B** 接通一次真实模型调用，输入一段课堂文字，返回一项任务草稿、原话依据和缺失信息。
- [ ] **T2｜B** 检查返回数据是否符合接口格式；无任务、服务失败和格式不合要求时返回明确状态。
- [ ] **T3｜B** 实现草稿保存、用户核对后的正式保存与重新读取。
- [ ] **T4｜A** 做一个最小核对页面：名称、DDL、原话、编辑、确认保存；不要先扩展完整首页。
- [ ] **T5｜A** 接上真实后端，显示处理中、成功、待确认和失败状态。
- [ ] **T6｜A＋B** 换一段内容运行，确认输出随输入变化，保存后刷新仍能读取。

**完成标准：**真实文字 → 模型提取 → 页面展示 → 用户确认 → 保存成功。此时第一次联调已经完成。

## 8. 学习助手 Agent 的接入清单

本节由 B 主责，与阶段三同步建立，随后在音频、日程和变更阶段逐步扩展。Agent 是产品运行时的学习助手；你们用来写代码的 AI 是开发工具，两者职责不同。

```text
前端提交输入
  → 后端准备转写、已有任务和用户明确反馈
  → 学习助手 Agent 调用模型及获准的查询／建议工具
  → 后端检查结果，返回草稿或变更建议
  → 前端让用户核对
  → 用户确认后，后端执行正式保存和提醒更新
```

- [ ] **G1** 把已确认的产品规则整理成运行时提示词，并由程序实际加载；把规则写在 Markdown 或 `AGENTS.md` 中，不会自动接入产品。
- [ ] **G2** 接入一个模型，传入本次转写、有关的已有任务和必要的日期上下文，不把全部历史无差别塞入每次请求。
- [ ] **G3** 提供读取已有任务、读取原话片段、提出任务草稿、提出日程／变更建议的工具；第一版保持一个学习助手 Agent。
- [ ] **G4** 给工具约定输入和输出，检查任务标识、日期、关联来源；不能只信模型生成的任意字段。
- [ ] **G5** 正式任务修改与提醒更新走用户确认后的后端操作；模型返回“已完成修改”不代表实际保存成功。
- [ ] **G6** 为模型调用和工具执行设置超时、有限重试和调用次数上限，失败后给出可重试的结果。
- [ ] **G7** 记录本次输入标识、模型结果、工具调用结果和保存结果，足以定位失败；日志不输出密钥。
- [ ] **G8** 用有任务、无任务、无 DDL、延期和任务关联不明的样例检查行为。录音中的文字是待分析材料，不能作为跳过用户确认的操作授权。

转写、页面、数据保存和提醒都需要应用代码；仅写提示词无法完成整个产品。不为第一版预先加入多 Agent、知识库或复杂的工具管理界面。

## 9. 阶段四：接入真实音频和 3 项任务

依赖：阶段三跑通。A、B 可在共同接口基础上并行推进。

- [ ] **R1｜B** 实现音频上传、格式和大小限制、文件读取及明确的失败返回。
- [ ] **R2｜B** 接入实际语音转写，保留时间片段，并把转写交给 Agent。无时间片段的服务不能冒充已支持精确回听定位。
- [ ] **R3｜B** 提取多项任务，区分原话要求与建议；无明确 DDL 时不补造期限，归属不清先保留为待确认。
- [ ] **R4｜A** 实现选择文件、上传状态、处理状态和原声播放。
- [ ] **R5｜A** 实现任务集中展示、原话查看、点击回听、修改和一次确认；待确认项明显标出。
- [ ] **R6｜B** 处理重复上传或重复确认，避免同一操作重复创建任务；必要时提示用户这是重复录音。
- [ ] **R7｜A＋B** 用第一段音频完整生成并保存 3 项作业，检查名称、截止时间、原话和回听位置。

**完成标准：**真实音频能进入真实转写和提取链路。不能仍依靠手工粘贴文字或固定任务卡作为最终演示结果。

## 10. 阶段五：建议日程和应用内提醒

依赖：有已确认的任务记录。

- [ ] **L1｜B** 根据已确认任务和期限生成按天的建议日程，用户无需填写空闲时间或工作量。
- [ ] **L2｜B** 大任务拆成 3–5 个可修改步骤，小任务保持一项；估计和 AI 建议单独标注。
- [ ] **L3｜B** 检查建议日期与 DDL 是否矛盾。时间紧张时明确提示，不暗中删减老师要求，不宣称保证完成。
- [ ] **L4｜A** 展示“当前一步”、简短理由和完整日程，并提供接受、调整入口。
- [ ] **L5｜B** 生成提醒记录：普通任务每天合并一条“今日建议”，默认晚上 7 点；有明确 DDL 的任务前一天提醒，同日截止尽量合并。
- [ ] **L6｜A** 做应用内提醒列表和时间修改／关闭入口；页面说明当前 Demo 的提醒运行范围。
- [ ] **L7｜A＋B** 页面运行期间，用可控的演示时间或短间隔触发一次提醒，验证确实按记录出现。若使用演示时钟，需要明确标注；仅有一张静态卡片不能算触发成功。
- [ ] **L8｜A＋B** 检查无明确 DDL 的任务不出现“即将截止”，无回应不自动顺延、不追加催促。

**完成标准：**任务确认后能生成可调整日程和提醒记录，应用打开时的提醒行为可实际验证。关闭网页后的提醒与手机锁屏通知在后续阶段单独验证。

## 11. 阶段六：延期识别与用户确认后更新

依赖：音频、任务保存、日程和提醒记录都已跑通。

- [ ] **C1｜B** 将第二段录音转写，与已有作业结合分析，提出候选任务和新期限。
- [ ] **C2｜B** 关联信息不足时返回候选或待确认问题，不直接覆盖同名任务。
- [ ] **C3｜A** 展示“原安排 → 新安排”和原话，提供确认、选择对应任务、放弃变更的入口。
- [ ] **C4｜B** 用户确认后更新原任务，保留原任务标识；同步调整相关日程、停用旧提醒并生成新提醒。
- [ ] **C5｜B** 防止重复点击、重复提交或过时的变更确认造成重复提醒、覆盖较新的任务内容；整组更新失败时不要展示为全部成功。
- [ ] **C6｜A＋B** 完整演示一次延期：确认前原任务不变，确认后各处一致，刷新后仍正确。

**完成标准：**第二段音频能改变第一段生成的正确作业，且旧期限提醒失效。这是最小 Demo 的最后一个核心功能关卡。

## 12. 核心 Demo 跑通后的第一批完善

这些事项属于已讨论的产品方向，但不应阻塞先交付第 3 节的可运行演示。两人按顺序补齐，未完成的行为在演示说明中如实列出。

- [ ] **E1｜A＋B** 完成按钮：更新任务状态，停用后续相关提醒；误操作可通过编辑恢复。
- [ ] **E2｜A＋B** “还没做”：生成新建议日程，接受后生效；不需要填写完成百分比。
- [ ] **E3｜A＋B** 部分完成：勾选已经完成的小步骤，后续日程保留这些进度。
- [ ] **E4｜A＋B** “换个时间”：修改建议执行日期或提醒时间，不能误改老师要求的截止时间。
- [ ] **E5｜A＋B** 取消任务：展示原话与取消建议，确认后停用日程和提醒。
- [ ] **E6｜A＋B** 归属不清、建议阅读与必交作业：明确展示待确认或可选性质，未确认归属的任务不当作本人必须完成的作业排入日程。
- [ ] **E7｜A＋B** 已过期、录入时已错过前一天提醒、任务堆积：补齐合理处理，不补发一串历史提醒、不静默改变 DDL。
- [ ] **E8｜B 主责，A 做入口** 删除演示录音／任务，明确关联转写、草稿、日程、提醒的处理方式，便于重新演示。
- [ ] **E9｜A＋B** 检查日期准确到天但没有钟点、时区变化和跨日的边界，避免把日期误显示为另一天。

## 13. 阶段七：验收、运行说明和演示交付

测试是验证行为，不是只检查代码能否启动。A 测操作流程，B 测后端与模型结果，关键改动一起复查。

| 必验情况 | 应看到的结果 |
| --- | --- |

## 14. 两个人和两套 AI 怎么配合

### 每次开工

1. 同步双方认可的最新版本、接口约定和当前待办；各自使用独立目录与分支。
2. 明确本次只做哪一项、改哪些模块、交付什么；让 AI 先读已有文档和代码。
3. 修改公共数据格式、项目依赖、启动方式前，先告知另一人并同步约定。
4. 按项目的依赖安全规则操作，不让两边的 AI 各自随意增加框架或覆盖配置。

### 每次交接

```text
本次完成：
修改的文件：
接口是否变化：
实际运行的检查及结果：
如何启动／复现：
未完成或已知问题：
对方下一步需要做什么：
```

每完成一个阶段就合并检查，至少每天收工前跑一次完整流程。提交和合并前检查自己的改动，避免覆盖对方工作。推送、添加协作者和发布按仓库授权约定执行，本清单不代为执行这些操作。

### 给 A 的 AI 的任务说明

> 我负责 AnchorLearn 的前端、交互和组织整合。先阅读项目规则、方案和共同接口文档。按当前待办完成上传／播放录音、任务核对、日程或提醒页面，调用 B 提供的接口。第一步只接通一项作业的展示、编辑和确认保存。临时示例数据需明确标注，完成后接上真实接口。遇到接口不一致先指出差异，不静默修改后端约定。报告修改文件、实际验证结果和仍未完成的内容，不擅自发布或新增依赖。

### 给 B 的 AI 的任务说明

> 我负责 AnchorLearn 的后端、音频转写、学习助手 Agent、日程和数据保存。先阅读项目规则、方案和共同接口文档。第一步用真实课堂文字调用模型，返回一项带原话依据的任务草稿，并支持用户确认后保存；接通前端后再加入音频转写、多任务、日程和延期识别。规则提示词必须由程序实际加载。缺失 DDL 不编造，改期确认前不覆盖正式记录。报告接口格式、实际运行方法、验证结果和未完成事项，不擅自发布或新增依赖。

## 16. 你们马上照着做的顺序

1. **现在：**你补齐预赛稿人员信息、确认产品名、完成提交。
2. **提交后：**两人确定开发环境、服务可用性和共同接口，准备两段音频。
3. **第一次联调：**B 让模型从文字中提取一项作业，A 展示并确认保存。
4. **第二次联调：**接音频上传、真实转写、3 项任务和原声核对。
5. **第三次联调：**接建议日程与应用内提醒。
6. **第四次联调：**接延期录音和确认后更新，完成核心演示。
7. **之后：**补进度反馈、取消和异常处理；跑验收、整理运行说明，再评估 SDK 和手机端。

每一步以可运行结果结束；跑不通时修复当前步骤，不继续堆功能。本文中的 24 小时原型目标来自预赛规划，不能代替实际工期评估，也不要求两个初学者按固定小时数赶工。
